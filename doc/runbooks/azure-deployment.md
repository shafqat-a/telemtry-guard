# Runbook: Azure deployment

P2-04 (Phase 2). Audience: whoever operates the Azure subscription/resource group
this environment deploys into. This is an operator runbook, not application code —
the deployable artifacts are the repo-root `Dockerfile`, `infra/azure/**` (Bicep),
and `.github/workflows/deploy.yml`. Edge/Cloudflare configuration is a separate,
already-written runbook — see [`cloudflare-fronting.md`](cloudflare-fronting.md) —
this document only covers the parts specific to hosting on Azure (D16) and links to
that one rather than repeating it.

**No Azure credentials exist in the environment that authored this runbook, and
nothing here has been run against a real subscription.** Every command below is
written from the Bicep templates and the deploy workflow, not verified against a
live deployment. Treat the first real run as the actual validation.

## 1. Compose → Azure mapping

| Compose service | Azure target | Notes |
|---|---|---|
| *(none — API runs on the host)* | Container App `tguard-api-<env>` | 1 replica, ingress 8080, Cloudflare-only IP allow-list, OTel sidecar |
| migration runner | Container Apps **jobs** `tguard-migrate-sql-<env>`, `tguard-migrate-clickhouse-<env>` | same image as the app, `dotnet /app/migrator/TelemetryGuard.MigrationRunner.dll [--clickhouse]`; run **before** the app rolls |
| `mssql` | Azure SQL Database, `GP_S_Gen5` serverless, auto-pause disabled | `ConnectionStrings__Main`; migrations and RLS unchanged (D8/D10/D11) |
| `redis` | Azure Cache for Redis (Basic C0 dev / Standard C1 prod), TLS-only 6380 | `ConnectionStrings__Redis`; connection-string change only (D5) |
| `clickhouse` | Ubuntu 22.04 VM in `snet-data`, no public IP, `clickhouse/clickhouse-server:24.8` on a Premium SSD | `Analytics__ClickHouse__ConnectionString`; provider code unchanged (D6/D7) |
| `grafana` | Azure Managed Grafana (optional, `deployGrafana=false` by default) | dashboards imported from `ops/grafana/dashboards/*.json` |
| OTLP collector | OTel Collector sidecar → Application Insights | env-var only, per API-01 (`OTEL_EXPORTER_OTLP_ENDPOINT`) |
| *(logs)* | Log Analytics `ContainerAppConsoleLogs_CL` | the app's `AddJsonConsole` output needs no agent |
| *(none)* | **`TelemetryGuard.Portal` — NOT deployed by this task** | P2-03's operator UI is a separate Razor Pages web app needing its own image, Container App and hostname (deliberately *not* behind the tracker origin's Cloudflare-only IP allow-list). Run it on a host with `dotnet run --project TelemetryGuard.Portal` until a follow-up deployment task lands. |

## 2. Edge chain

Cloudflare (DNS proxied, Full (strict), Worker, cache-bypass rules — see
[`cloudflare-fronting.md`](cloudflare-fronting.md) for the full procedure) → Container
Apps ingress. **No Azure Front Door** (D13 — Front Door does not pass JA3/JA4 to
origin, so Cloudflare must stay the outermost edge even in front of Azure). Origin
lockdown is the `ipSecurityRestrictions` allow-list on the Container App's ingress
(one `Allow` rule per IPv4 CIDR in `TelemetryGuard.Api/Edge/cloudflare-ips.txt`,
regenerated by the deploy workflow on every run). After running
`scripts/update-cloudflare-ips.sh`, redeploy so both the app's *embedded* list
(compiled into the image, used for `ForwardedHeaders`/`EdgeSignalReader`) and the
*ingress* allow-list agree — they are two independent copies of the same data and can
drift if only one side is redeployed.

## 3. First-deploy order

1. Create the resource group.
2. Grant the OIDC identity (the one the `deploy.yml` workflow federates as) **Owner**
   on the resource group — Contributor alone cannot create the role assignments the
   Bicep modules provision (`AcrPull` in `registry.bicep`, `Key Vault Secrets User` in
   `keyvault.bicep`).
3. Set the GitHub repository secrets (section 5 below).
4. Run the `Deploy (Azure)` workflow (`workflow_dispatch`, or push to `main`).
   - `build-push` bootstraps the ACR (idempotent — see the comment in
     `infra/azure/modules/registry.bicep`), builds and pushes the image, imports the
     OTel Collector image into ACR.
   - `infra` deploys everything **except** the app (`deployApiApp=false`): network,
     observability, SQL, Redis, the ClickHouse VM, Key Vault, and both migration jobs.
5. Wait for the ClickHouse VM's cloud-init to finish before running migrations:
   ```bash
   az vm run-command invoke -g <rg> -n tguard-ch-<env> \
     --command-id RunShellScript --scripts "docker ps"
   ```
   Expect a running `clickhouse` container in the output. cloud-init typically takes
   a few minutes after the VM first boots; the migration job will simply fail and can
   be re-run if it races this.
6. `migrate` runs both migration jobs (SQL, then ClickHouse) and gates the rest of the
   deploy on their success.
7. `deploy` rolls out the app (`deployApiApp=true`). Because the API's readiness probe
   includes `ClickHouseHealthCheck`, the new revision will not go healthy — and
   Container Apps' single-revision mode will not shift traffic to it — until the VM
   and SQL/Redis are all reachable. This is the intended ordering guard, not a bug.
8. `smoke` confirms the active revision is `Healthy`/`Provisioned`.

## 4. Custom domain + Cloudflare binding

The step most likely to bite: `infra/cloudflare/tg-edge-worker.js` forwards the
request with the tenant-facing `Host` header unchanged, so the Container App **must**
have that hostname bound, or ingress returns 404 (Container Apps routes by the `Host`
header among bound custom domains). On the very first deploy `customDomainName` is
empty and the app is reachable only at its default `*.azurecontainerapps.io` FQDN
(output `apiFqdn`) — fine for the `infra`/`migrate`/`deploy` sequence, not yet usable
behind Cloudflare.

To bind the real hostname:

1. Temporarily set the DNS record to **DNS-only (grey cloud)** in Cloudflare — this
   lets Azure's domain-ownership verification reach the origin directly.
2. Add the `asuid.<host>` TXT record Azure requests (Container Apps custom-domain
   verification).
3. Obtain a **Cloudflare Origin CA certificate** (dashboard → SSL/TLS → Origin
   Server) for the hostname — Full (strict) mode accepts Origin CA certs, and using
   one avoids the Container Apps managed-certificate renewal path failing behind a
   proxy that intercepts the ACME HTTP-01 challenge.
4. Upload that certificate as a `Microsoft.App/managedEnvironments/certificates`
   resource (`az containerapp env certificate upload`) and note its resource id.
5. Re-enable the orange cloud in Cloudflare.
6. Redeploy with `customDomainName=<host>` and
   `customDomainCertificateId=<the certificate resource id>` set (either edit the
   relevant `params.<env>.json` or pass `-p` overrides on the next workflow run).

## 5. Secrets

**What Bicep writes to Key Vault** (see `infra/azure/modules/keyvault.bicep`) —
computed from other modules' outputs plus the three `@secure()` parameters the
workflow supplies from GitHub secrets:

| Secret | Source |
|---|---|
| `sql-connection-string` | Built from `sql.bicep`'s output FQDN + `sqlAdminLogin`/`sqlAdminPassword` |
| `redis-connection-string` | Built from `redis.bicep`'s output host name + primary key |
| `clickhouse-connection-string` | Built from the fixed private IP/db/user + `clickHousePassword` |
| `beacon-hmac-secret` | Passed straight through from the `beaconHmacSecret` parameter |
| `appinsights-connection-string` | `observability.bicep`'s output connection string |

**What the operator seeds by hand** (never created by Bicep — `integrationSecretsEnabled`
stays `false` until these exist): `turnstile-secret-key`, `turnstile-site-key`,
`googleads-developer-token`, `googleads-oauth-client-id`,
`googleads-oauth-client-secret`, `googleads-oauth-refresh-token`,
`meta-system-user-token`. Seed with:

```bash
az keyvault secret set --vault-name <keyVaultName output> --name turnstile-secret-key --value <...>
```

Then flip `integrationSecretsEnabled=true` on the next deploy so the Container App's
`configuration.secrets`/env actually reference them.

**GitHub repository secrets `deploy.yml` reads** (all must be present for the
`preflight` gate to enable the rest of the workflow):
`AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `AZURE_RESOURCE_GROUP`,
`TG_SQL_ADMIN_PASSWORD`, `TG_CLICKHOUSE_PASSWORD`, `TG_BEACON_HMAC_SECRET`. Optional:
`TG_SMOKE_BASE_URL` (the Cloudflare-proxied hostname, enables the through-Cloudflare
smoke check). No client secret is stored anywhere — `azure/login@v2` federates via
OIDC (`permissions: id-token: write`).

**State this plainly to whoever asks "is it live":** until Turnstile keys are seeded,
INT-01 returns "unavailable" (fail-closed) and the 31–70 challenge band cannot
complete — every session in that score band degrades to whatever the fail-closed
policy resolves to, never to a working Turnstile challenge. Both exclusion-sync
workers (Google Ads, Meta) also stay in `EffectiveDryRun` until their credentials are
seeded *and* `DryRun` is explicitly set `false` — a fresh environment never mutates a
live ad account.

## 6. Tenant provisioning in a deployed environment

Never hand-write rows. Run the migrator's `provision` verb through the SQL migration
job with a one-off command override:

```bash
az containerapp job start -n <sql-job> -g <rg> \
  --command dotnet \
  --args "/app/migrator/TelemetryGuard.MigrationRunner.dll provision create-tenant --tenant-id <guid> --name <name> --retention-days 90 --enforcement-mode AutoEnforce"
```

This requires an `az` CLI new enough to support start-time command/arg overrides on
`containerapp job start`. If yours does not, the fallback is `az containerapp job
update` with the same `--command`/`--args`, run the job, then revert the job's
definition back to its normal migration invocation (`update` again, or redeploy the
Bicep template, which restores it).

## 7. Rollback

- **App**: `az containerapp update -n <app> -g <rg> --image <acr>/telemetryguard-api:<previous-sha>`.
  Single-revision mode shifts traffic once the rolled-back revision passes probes.
- **Migrations are never rolled back.** DbUp (SQL Server) and the ClickHouse
  `SchemaMigrator` are both forward-only. An incompatible schema change ships as a new
  additive migration, never an edit to an applied one.
- **ClickHouse VM**: restore the data disk from a snapshot (there is no in-place
  "undo" for the self-hosted node — take a disk snapshot before any operation you are
  not sure of).

## 8. Cost notes (indicative only — verify before quoting anyone)

These are **unverified estimates** that drift by region, by SKU pricing changes, and
over time. Price the exact SKUs below in the Azure pricing calculator before quoting
a number to anyone.

| Resource | SKU deployed | Rough monthly order of magnitude (dev sizing) |
|---|---|---|
| Azure SQL Database | `GP_S_Gen5`, serverless, `minCapacity=0.5`, capacity 2 (dev) / 4 (prod) | tens of USD at low utilization — **never auto-pauses in this design** (decision 7: the readiness probe and `RollupService` both poll SQL well inside any pause window, so the saving comes from the low `minCapacity` floor, not from pausing) |
| Azure Cache for Redis | Basic C0 (dev) / Standard C1 (prod) | low tens of USD |
| ClickHouse VM | `Standard_D2as_v5` (dev) / `Standard_D4as_v5` (prod) + 64 GB OS + 256 GB Premium SSD data disk | tens to ~100 USD |
| Container Apps environment + API app | Consumption workload profile, 1 replica pinned (`minReplicas: 1, maxReplicas: 1`) | **cannot scale to zero** — decision 5: the workers (rollup, grace sweep, exclusion syncs) live in the same process as the API, so the app must always have exactly one running replica |
| ACR | Basic | single-digit USD |
| Log Analytics + App Insights | PerGB2018, 30-day retention | usage-dependent, low at dev volume |
| Azure Managed Grafana | Standard (only if `deployGrafana=true`, default off) | tens of USD — left off by default to keep the dev bill honest |

Two honest corrections worth repeating to anyone comparing this to the Compose bill:
Azure SQL **never auto-pauses** here, and the API app **cannot scale to zero** because
the background workers live in it. Neither is a bug; both are documented, deliberate
trade-offs (decisions 5 and 7).

## 9. Sign-off checklist

Run through this after every first deploy to a new environment, and after any change
to the Bicep templates or the Dockerfile:

- [ ] `/healthz` returns 200 **through Cloudflare** (not by curling the origin directly).
- [ ] `/ready` returns 200 (all three dependencies — SQL, Redis, ClickHouse — reachable).
- [ ] `/sdk/tg.js` returns 200 with `Cache-Control: public, max-age=300, ...` and
      `/sdk/tg-<version>.js` returns 200 with `Cache-Control: public, max-age=31536000, immutable`.
- [ ] `dbo.SchemaVersions` contains **one row per `.sql` file** in
      `TelemetryGuard.Data/migrations/` at the deployed commit — compare the row count
      against `ls TelemetryGuard.Data/migrations/*.sql | wc -l` rather than naming
      migration numbers (sibling tasks add scripts in parallel).
- [ ] ClickHouse `tg_schema_migrations` is populated (via
      `docker exec clickhouse clickhouse-client --query "SELECT * FROM tg_schema_migrations"`
      over `az vm run-command`, or a tunnel).
- [ ] Application Insights shows request traces with **no application code change**
      (proves the OTel Collector sidecar → `azuremonitor` exporter path works).
- [ ] `X-TG-ASN` is observed on origin requests (re-run of the INT-05 acceptance check
      — confirms the Cloudflare Worker → `EdgeSignalReader` path is live end to end).
- [ ] `infra/azure/verify-rls.sql` run once against the environment
      (`sqlcmd -S <sqlServerFqdn output> -d TelemetryGuard -U tgadmin -P <password> -i infra/azure/verify-rls.sql`)
      — record its output; all three checks must show the expected row count.
- [ ] No secret value appears in any deployment output, `az` command echoed to a log,
      or workflow log (`main.bicep` has no output whose value is a secret by
      construction — the `outputs-should-not-contain-secrets` Bicep lint rule is set
      to `error` in `infra/azure/bicepconfig.json`).

## Known limitations / follow-ups (read before a real first deploy)

- **ClickHouse VM authentication**: `clickhouse-vm.bicep` sets
  `disablePasswordAuthentication: true` with no SSH public key configured, matching
  the task's pinned design (administration is exclusively `az vm run-command invoke`,
  never SSH — there is no inbound NSG rule for port 22). If your Azure environment's
  ARM validation rejects a Linux VM with no `adminPassword` and no
  `linuxConfiguration.ssh.publicKeys`, add an `sshPublicKey` parameter to that module
  plus an Azure Bastion (both intentionally out of scope here) rather than reusing
  another module's secret for VM login.
- **Bicep API versions**: pinned to the newest stable (non-preview) versions known at
  authoring time (see the comment near the top of `infra/azure/main.bicep`'s
  prerequisites in the task doc). If `az bicep build` reports an unknown type/version,
  bump to the current stable version for that resource type and note the change here.
- **Portal deployment**: intentionally out of scope — see the mapping table row above
  and P2-03's own task file. A follow-up task owns building and deploying a
  `TelemetryGuard.Portal` image, Container App, and hostname.
