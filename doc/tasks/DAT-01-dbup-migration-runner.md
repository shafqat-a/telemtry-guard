# DAT-01: DbUp migration runner

## Objective
Create a console project `TelemetryGuard.MigrationRunner` that applies versioned SQL migrations to SQL Server using DbUp (embedded scripts that live in the `TelemetryGuard.Data` project), and that — when invoked with `--clickhouse` — delegates ClickHouse schema application to ANA-02's `SchemaMigrator` (one applier, one journal). This runner is the single entry point by which any database schema reaches any environment (local, CI, prod). No EF migrations exist anywhere in this codebase.

## Spec context (self-contained)
- **D10 — Migrations are numbered SQL scripts run by DbUp, per store.** SQL Server and ClickHouse each migrate via plain scripts executed by one runner per store. RLS policies, security predicates, and indexes are first-class citizens written directly in `.sql` scripts — never generated by an ORM.
- **D9 — Dapper, not EF Core.** There are no EF migrations, no `DbContext`, no `migrationBuilder`. Do not add any EF package.
- **D1 — No server-side scripting languages.** The runner is a .NET console app. Do not introduce Python/Node scripts to run migrations.
- Solution shape (spec §8): `TelemetryGuard.Data` holds `/migrations/*.sql` for SQL Server; `TelemetryGuard.Analytics.ClickHouse` holds `/schema/*.sql` for ClickHouse (created later by ANA-02 — the runner must tolerate that directory not existing yet).

## Prerequisites
FND-01 has scaffolded `TelemetryGuard.sln` with the projects from spec §8, including the class library `TelemetryGuard.Data` (it may be empty). Locate the actual directory layout in the checkout (projects may sit at repo root or under `src/`); all paths below assume repo root — adjust the prefix to match FND-01's layout. If `TelemetryGuard.Data` does not exist yet, create it with `dotnet new classlib -n TelemetryGuard.Data` and add it to the solution.


3. **Prepare `TelemetryGuard.Data` to carry embedded migration scripts.**
   - Create the directory `TelemetryGuard.Data/migrations/` (empty of `.sql` files for now — DAT-02 adds `0001_core_schema.sql`).
   - Add to `TelemetryGuard.Data/TelemetryGuard.Data.csproj`:
     ```xml
     <ItemGroup>
       <EmbeddedResource Include="migrations\**\*.sql" />
     </ItemGroup>
     ```
   - Create the anchor type `TelemetryGuard.Data/MigrationsAnchor.cs` (used to locate the assembly containing the embedded scripts):
     ```csharp
     namespace TelemetryGuard.Data;

     /// <summary>Anchor type: the migration runner loads embedded migration scripts
     /// from this assembly. Never delete.</summary>
     public static class MigrationsAnchor
     {
     }
     ```
   - Create `TelemetryGuard.Data/migrations/README.md` with this content:
     ```markdown
     # SQL Server migrations (DbUp)

     - Naming: `NNNN_description.sql` (zero-padded 4-digit ordinal, ascending, never reused,
       never edited after merge — fix mistakes with a NEW script).
     - Scripts are EmbeddedResources; DbUp applies pending scripts in name order,
       one transaction per script, journaled in `dbo.SchemaVersions`.
     - `GO` batch separators are supported (required around CREATE SCHEMA / CREATE FUNCTION).
     - RLS RULE (see DAT-03): every migration that creates a new tenant-scoped table MUST
       `ALTER SECURITY POLICY rls.TenantIsolationPolicy` to add FILTER + BLOCK predicates for
       that table in the same migration. Only the resolution tables (dbo.ApiKeys, dbo.Sites)
       are exempt.

     ## Number registry (append when adding a script)
     | NNNN | Description | Task |
     |------|-------------|------|
     ```

4. **`TelemetryGuard.MigrationRunner/Migrations.cs`** — public so integration tests (DAT-08) and the analytics harness can invoke migrations programmatically. There is deliberately **no bespoke ClickHouse applier in this runner**: ANA-02's `SchemaMigrator` (in `TelemetryGuard.Analytics.ClickHouse`, embedded-resource scripts, journal table `tg_schema_migrations`) is the ONE mechanism that applies ClickHouse schema — two appliers with two journals would double-apply scripts. The `--clickhouse` switch merely delegates to it:
   ```csharp
   using DbUp;

   namespace TelemetryGuard.MigrationRunner;

   public static class Migrations
   {
       /// <summary>Creates the database if missing, then applies pending embedded
       /// scripts from TelemetryGuard.Data/migrations. Returns process exit code.</summary>
       public static int RunSqlServer(string connectionString)
       {
           EnsureDatabase.For.SqlDatabase(connectionString);

           var upgrader = DeployChanges.To
               .SqlDatabase(connectionString)
               .WithScriptsEmbeddedInAssembly(
                   typeof(TelemetryGuard.Data.MigrationsAnchor).Assembly,
                   name => name.Contains(".migrations.", StringComparison.OrdinalIgnoreCase))
               .JournalToSqlTable("dbo", "SchemaVersions")
               .WithTransactionPerScript()
               .LogToConsole()
               .Build();

           var result = upgrader.PerformUpgrade();
           if (!result.Successful)
           {
               Console.Error.WriteLine(result.Error);
               return 1;
           }
           Console.WriteLine("SQL Server migrations up to date.");
           return 0;
       }

       /// <summary>Delegates ClickHouse schema application to ANA-02's SchemaMigrator
       /// (single journal: tg_schema_migrations). While ANA-02's project does not yet
       /// exist in the checkout, this method is a tolerated no-op.</summary>
       public static async Task<int> RunClickHouseAsync(string connectionString)
       {
           // TODO(ANA-02): once TelemetryGuard.Analytics.ClickHouse exists, add the
           // project reference (csproj comment above) and replace the block below with:
           //   var applied = await new TelemetryGuard.Analytics.ClickHouse
           //       .SchemaMigrator(connectionString).ApplyAsync();
           //   foreach (var name in applied) Console.WriteLine($"Applied ClickHouse script {name}");
           //   Console.WriteLine("ClickHouse schema up to date.");
           //   return 0;
           Console.WriteLine("TelemetryGuard.Analytics.ClickHouse (ANA-02) not present; nothing to apply.");
           await Task.CompletedTask;
           return 0;
       }
   }
   ```
   Do NOT re-introduce a file-globbing/statement-splitting applier or a second journal table here — `SchemaMigrator` owns script discovery (embedded resources), statement splitting, and journaling (`tg_schema_migrations`); the pre-ANA-02 `tg_schema_versions` journal from earlier drafts is dead.

5. **`TelemetryGuard.MigrationRunner/Program.cs`** (full file):
   ```csharp
   using TelemetryGuard.MigrationRunner;

   if (args.Contains("--clickhouse", StringComparer.OrdinalIgnoreCase))
   {
       var chCs = Environment.GetEnvironmentVariable("CLICKHOUSE_CONNECTIONSTRING");
       if (string.IsNullOrWhiteSpace(chCs))
       {
           Console.Error.WriteLine("CLICKHOUSE_CONNECTIONSTRING environment variable is not set.");
           return 2;
       }
       return await Migrations.RunClickHouseAsync(chCs);   // delegates to ANA-02's SchemaMigrator
   }

   var cs = Environment.GetEnvironmentVariable("MIGRATIONS_CONNECTIONSTRING");
   if (string.IsNullOrWhiteSpace(cs))
   {
       Console.Error.WriteLine("MIGRATIONS_CONNECTIONSTRING environment variable is not set.");
       return 2;
   }
   return Migrations.RunSqlServer(cs);
   ```

6. **Wire into CI (FND-03's workflow).** If `.github/workflows/ci.yml` exists and has an integration job with a SQL Server service container, add this step *before* the integration-test step (adapt the SA password/port to what the job defines):
   ```yaml
   - name: Apply SQL Server migrations
     env:
       MIGRATIONS_CONNECTIONSTRING: "Server=localhost,1433;Database=TelemetryGuard;User Id=sa;Password=${{ env.MSSQL_SA_PASSWORD }};TrustServerCertificate=True"
     run: dotnet run --project TelemetryGuard.MigrationRunner --configuration Release
   ```
   If the workflow does not exist yet, or the integration job uses Testcontainers only (tests run migrations themselves via `Migrations.RunSqlServer` — see DAT-08), skip this step and leave a note in the PR description that FND-03 should add it when a shared service container appears.

## Acceptance criteria
- `dotnet build TelemetryGuard.sln` succeeds.
- With a disposable SQL Server running (`docker run -e ACCEPT_EULA=Y -e MSSQL_SA_PASSWORD='Your_password123' -p 1433:1433 -d mcr.microsoft.com/mssql/server:2022-latest`):
  - `MIGRATIONS_CONNECTIONSTRING="Server=localhost,1433;Database=TelemetryGuard;User Id=sa;Password=Your_password123;TrustServerCertificate=True" dotnet run --project TelemetryGuard.MigrationRunner` exits 0, creates database `TelemetryGuard` and table `dbo.SchemaVersions` (zero scripts applied is a valid success while `migrations/` has no `.sql` files yet).
  - Running the same command a second time exits 0 and applies nothing (journal honored).
- `dotnet run --project TelemetryGuard.MigrationRunner -- --clickhouse` with `CLICKHOUSE_CONNECTIONSTRING` set but ANA-02's project not yet in the checkout exits 0 and prints the "not present; nothing to apply" message. (Once ANA-02 lands and the delegation is wired, the same command applies its scripts journaled in `tg_schema_migrations` — the ONLY ClickHouse schema journal; `grep -rn "tg_schema_versions" TelemetryGuard.MigrationRunner/` finds nothing.)
- Running without `MIGRATIONS_CONNECTIONSTRING` exits 2 with an error on stderr.
- No EF Core package appears in any `.csproj`.

## Testing
- No dedicated unit-test project changes in this task; the runner is exercised end-to-end by the acceptance commands above and programmatically by DAT-08 (`Migrations.RunSqlServer(connectionString)` must remain `public static`).
- Manual check: `sqlcmd -S localhost,1433 -U sa -P 'Your_password123' -d TelemetryGuard -Q "SELECT * FROM dbo.SchemaVersions"` returns an (empty) journal table.

## Out of scope / guardrails
- Do NOT write any migration scripts here — DAT-02/DAT-03/DAT-06/DAT-07 own the SQL Server scripts; ANA-02 owns the ClickHouse schema files.
- Do NOT add EF Core, `DbContext`, or EF migrations anywhere (spec D9/D10 — Dapper + DbUp only).
- Do NOT introduce Python/Node/shell-scripted migration tooling (spec D1 — .NET end-to-end).
- Do NOT build a generic cross-engine migration abstraction: SQL Server and ClickHouse are two separate, explicitly-coded paths in one runner (spec D7 — abstract by intent, never a cross-engine layer).
- `Migrations.RunSqlServer` and `Migrations.RunClickHouseAsync` must stay `public` — DAT-08 and the analytics test harness call them.
- The ClickHouse path is delegation-only: script discovery, statement splitting, and journaling (`tg_schema_migrations`) belong to ANA-02's `SchemaMigrator`. Never add a second applier or journal in this runner.
